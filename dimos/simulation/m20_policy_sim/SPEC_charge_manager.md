# Differences to fix (ordered by risk to the robot)

Line numbers are at HEAD c38db167d6. "log" means all_cm.log. "Decompile only" means the branch never ran in the logs.

1. **An undock in JointDamping (soft e-stop) stands the robot up.** Vendor 0x203908 (DoOverChargeTask) and 0x1801b8 (exitPileAction); the same check is in 0x203760 / 0x180bc0.
   - Vendor: if the motion state is 2, it warns "软急停，退出退桩操作", returns 0x1008 (error, then idle) and writes nothing.
   - Ours: Request::Undock (D:937-960) checks no motion state, and since c38db167d6 no fault either. It goes on to stand_up (D:973), which writes MotionState 1 and then 17.
   - Test: charging, view.state = JointDamping, Request::Undock. Assert no MotionState write in `take_writes()` and that it ends idle with 0x1008.

2. **No obstacle check until a body height arrives.** Vendor 0x1fd810 / 0x1f9ba8.
   - Vendor: the check always runs, using the last MotionInfo.height.
   - Ours: detector_module.rs:258-262 publishes nothing without a height, so obstacle avoidance is silently off.
   - Test: open the check with no body_height and a 20-point block 0.5 m ahead. Assert a reading is published, or the dock is refused / a warning logged.

3. **The no-charge retry goes from lying straight to rl_control.** Vendor 0x1814e0, which calls StandUp2WideWalk 0x1f4c90.
   - Vendor: MotionState 1, sleep 2 s, then MotionState 17 + Gait 0x3001; then sleep(2), 5× Steer(-0.8, 0, 0), then the stale (0, 0, 0, -1.1). Log 2026-11-06 05:01:40: new:1, then new:17 / 0x3001 at +3 s.
   - Ours: D:1418-1424 `set_target(RlControl)` writes MotionState 17 + Gait immediately, with no stand and no kicks. Its failure also ends the sequence, where the vendor ignores StandUp2WideWalk's result on this path.
   - Test: in sim_sequence `dock_without_charge_retries_then_backs_off`, `record_writes()`. After the first no-charge, assert the writes are MotionState(1), then MotionState(17) + Gait(0x3001) about 2000 ms later, then 5× Steer{x:-0.8} and Steer{z:-1.1} about 2000 ms after that.

4. **Ours folds every vendor error code into "Idle + failed", so the follow-up behaviour is wrong.** Vendor 0x17fdb0 (DoExcepHandlingProcess) and 0x182298 (Start, error state).
   - **Vendor, by code:**
     - 0x1005 (approach 60 s / WideWalk failed): automatic exitPile.
     - 0x1002 (detector restart failed): SitDown re-issued every ~3 s (log: 289 calls for one error).
     - 0x1003 / 0x1004 / 0x1008 / INITNULL: plain idle (log: 55× 0x1004 → idle).
     - 0x1006 / 0x1009 / 0x100a: stays in error ("My status is [error]" every 3 s) until undock or cancel.
     - In error, a dock (cmd 1) never starts a dock.
   - **Ours:** every Failure ends the sequence via finish(…, error=true), giving Idle with `failed=true` (D:1108-1120, D:1158, D:1350).
     - `failed` permits an undock from idle, which the vendor ignores in idle.
     - `failed` blocks the idle loop's charge-take (D:606), which the vendor does after 0x1004 / 0x1008.
     - Cancel does not clear `failed` (D:881-900).
     - A Dock request from the error state is accepted (D:902).
   - **Test:** one test per code in docking/tests.rs:
     - FindTarget timeout → idle, undock refused, a later charge taken by the idle wake.
     - Obstacle 10 s → error, Dock refused, Undock accepted, Cancel → idle.
     - Restart failure → repeated MotionState(4) writes every ≥3 s.
     - Approach 60 s → exitPile starts.
   - The last of these is decompile only: 0 occurrences of "more than 1 min" in the log. Copying it faithfully means the 5 back-off kicks in BasicFlat followed by a 0x1008; decide deliberately.

5. **NoChargePlug_way = "sitDown" is not modelled.** Vendor 0x1823xx (Start, goToPile ret 0x1007).
   - Vendor: SitDown, error 0x1007, CloseMark. Then DoExcep runs Open12vPower(3) back to back and takes a charge when it comes.
   - Ours: D:1432-1436 sets Phase::Charging and leaves `charge_cmd` / `charge_checked` as whatever the last charge left them. With `charge_cmd=false` it waits forever with no writes; with true, it errors 0x1007 at the first check.
