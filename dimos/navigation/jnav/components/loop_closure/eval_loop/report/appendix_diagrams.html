How GSC works

1. Keyframing

Every lidar scan arrives with the odometry pose at its time. A scan becomes a keyframe when the robot has moved more than keyframe_min_distance_meters (0.5 m) or turned more than keyframe_min_rotation_degrees (10°) since the last keyframe. Keyframes keep their scan in the body frame, so a corrected pose re-places the whole scan.

since last keyframe?}
  K -- no --> P[publish corrected odometry + tf

body-frame cloud, odometry pose,

  KF --> D[scan-context descriptor
20 rings x 60 sectors + ring key]
  KF --> P
  D --> G[closure search: see 2]

2. The gates a loop closure passes

Stages 1-2 run on the worker thread at every keyframe. Stages 3-4 run on the closure-search thread, one search at a time. The outcome names below are the ones in the loop analysis lists.

  O -- no --> R1([low_occupancy])
  O -- yes --> C{scan-context match
cosine distance < 0.4 among top 10
else nearest keyframe within 3 m}

  C -- candidate --> Q{best waiting proposal?
one slot, ranked by similarity}
  Q -- beaten --> R3([outranked])
  Q -- search thread free --> I[ICP: source scan onto target submap
target keyframe +-5, 50 iterations]
  I --> DG{normal-scatter degeneracy

  DG -- no --> R4([degeneracy_reject])
  DG -- yes --> IG{converged and fitness <= 0.15?
fitness = inlier MSE / overlap fraction}
  IG -- no --> R5([icp_reject])
  IG -- yes --> U{fitness < what the graph already knows
between the two keyframes?}
  U -- no --> R6([uninformative])
  U -- yes --> Y{confidence >= 1 - exp(-z^2/2)?
z = yank in robust std devs per sqrt gap}
  Y -- no --> X{extended ICP on the last 2,4,8,16 keyframes

3. Compute and backpressure

The live module never lets a slow stage stall the scan stream. Scans wait in a bounded queue, and the oldest are dropped past 5. Closure search and the pose-graph solve each run on their own thread. A finished solve wakes the worker, which adopts it at once.

4. Pressure and need: when to spend extra effort

Extra work (checking more scan-context candidates, stacking more keyframes into ICP) is only spent when two things both say so. Pressure says a loop is likely right now. Need says the match in hand isn't convincing enough yet. Otherwise GSC does exactly the cheap single-scan check.

  • Pressure: are we probably back somewhere old that no closure has tied in yet? This is unresolved_loop_probability. Each earlier keyframe's position as seen from the newest one has an uncertainty: from the solved graph (Takahashi covariance recovery after each solve), plus the odometry since that solve. Each earlier keyframe gets the chance the newest scan overlaps it (probability product kernel against the scans' average reach). That chance is weighted by how likely the keyframe is off by more than closure_search_radius, since the position search would find it otherwise. Recomputed every pressure_check_frequency scans (default 5) and published on debug_log. It rises before real loops and drops once they close.
  • Need: how convincing must this match be? Evidence = −ln(1 − confidence), confidence = scan-context × ICP × degeneracy factors. Required evidence = the yank part (bigger corrections need more proof) + the solve's record (if it has lately rejected more closures than it kept, add ln((1 − keep_rate) / keep_rate), never below 0) + ln(look-alike places) (picking one of N places the scan fits equally well).
  • Rule 1, widen the scan-context search: as far as pressure allows, and only while more look-alikes could change the answer. After ICP, look-alike places are counted in ring-key order up to e^(evidence − bar), the point where one more look-alike would make the match not convincing. Candidates checked are capped at scan_context_top_k / (1 − pressure): today's 10 when no loop is expected, more as pressure rises.
  • Rule 2, extend ICP: as far as pressure allows, and only while the match isn't convincing yet. Extended ICP stacks 2, 4, 8 … keyframes while evidence < required, up to closure_extended_icp_max_keyframes × pressure keyframes. As evidence grows it may count further look-alikes. Out of budget, the match is rejected for now and can come back when pressure is higher.

Status: pressure (debug_log, pressure_check_frequency) is committed (mls_reform e4665e32c1). Rules 1–2 and the need terms are under test on Go2 L1 and Mid-360 and not committed yet.
