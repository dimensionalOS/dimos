# High level

## Reference Optimal Local Planner

This folder contains optimal local planner (5-10m range)

It was first developed "in theory" in static handcrafted and autogenerated 2D worlds.
The refenrece planner during development was allowed to be slow, but good. It would accept different body dimensions and locomotion systems

Those worlds, the reference itself and the judge that scores against it are the
benchmark, and the benchmark is not on this branch - see "What is not here".


## Implementation Local Planner

An evo lab wrapped around that benchmark produced a runtime planner that behaves close to
the reference but runs in milliseconds. The crate it produced is what `planner/rust/` is,
and it carries its own behavioural invariants (`rust/tests/invariants.rs`, five of them):
routes an open world, refuses a sealed box, never hops a thin wall, answers the same way
every call, and memoizes nothing across calls. See [tools.md](tools.md) for the command.


## Real2Sim Simulation — NOT ON THIS BRANCH

A module controlling the go2 was pulled out of its binaries and hosted in mujoco; IRL
body motion was recorded with a VR tracker along with every message going into it,
replayed in sim, and a judge scoring base_link divergence between reality and simulation
drove an optuna fit of the physics. That matched env is what every speed number below
was measured in. It lives on `ivan/feat/trajectory_ctrl` (`motion/simulation/`) — see
"What is not here".

# Technical Structure

Local motion: plan a path around obstacles, walk it, prove both work.

`planner/` and `control/` were built the same way, on purpose: a **runner** that
picks a candidate, a **referee** that scores it, and **research/** where candidates
come from. One referee per side is what makes the shipped law, an autoresearch lab's
and a learned one comparable by construction. This branch is the shipped halves only
-- the referees and the labs are on `ivan/feat/trajectory_ctrl` ("What is not here",
below), so what is here is what a robot runs:

```
embodiment/     base.py Embodiment · go2.py the measured Go2 · synthetic.py test bodies

planner/                             control/
  planners/     registry, se2 search,  controller.py tracks.py profile.py
                target candidate
  rust/         production crate       laws/ rust/   the shipped laws
```

Messages are stock `dimos.msgs`. There used to be a `types.py` here holding a
faster copy of `Vector3`/`Quaternion`/`Pose`/`Path`, because the real ones cost
107 µs per `PoseStamped` — `episode.plan()` builds a 55-207 pose `Path` inside
the referee's `process_time` window against a 20 ms budget, so the copy was
load-bearing, not stylistic. Once `dimos.msgs` stopped routing `__init__`
through `plum` (0.42–1.79 µs now) the copy lost its reason and was deleted.
Worth knowing before anyone adds dispatch back to a message constructor.

## What is not here

This branch is the algorithms and their deployment. Everything that trains, searches or
simulates stayed on **`ivan/feat/trajectory_ctrl`**, which is where to go to re-measure
any number quoted in these files:

- `simulation/` — the matched Go2 MuJoCo env (physics fitted to two real recordings).
  Every speed, envelope and slip constant here was measured in it.
- `planner/referee/` — the planner's benchmark: the worlds, the SE(2) gold oracle, the
  judge and its invariance tests, plus the `--score` runner over them.
- `control/referee/` — the closed-loop executor referee: episode runner, judge, battery,
  walk-slip probe. It drives that MuJoCo plant, so it goes with it.
- `planner/research/`, `control/research/` — the evo labs and the learned candidates.

The labs themselves live outside the repo entirely: an autoresearch loop needs write
access to its candidate and none to the referee scoring it.

## I/O — everything is stock dimos msgs

**MotionPlanner** (adapter)

# local map is what we internally call "local global" - accumultad map around the robot

- in: `local_map: sensor_msgs.PointCloud2` — raycaster cloud
- in: `odometry: nav_msgs.Odometry` — own pose (pointlio, `odom` frame)
- in: `planner_path: nav_msgs.Path` — global path; the goal is a carrot along it
- out: `path: nav_msgs.Path` — the local plan. Per-waypoint `ts` deltas encode
  required precision (`dt = segment / governor_speed(clearance)`, see
  `control/profile.py`); a single-pose path means "hold, no safe route"

**TrajectoryFollower** (adapter)

- in: `path: nav_msgs.Path` — stamped or plain (flat `ts` just disables the hint)
- in: `odometry: nav_msgs.Odometry`
- in: `local_map: sensor_msgs.PointCloud2` — optional, richer clearance hint;
  without it the follower decodes the path stamps instead
- in: `stop_movement: std_msgs.Bool`
- out: `nav_cmd_vel: geometry_msgs.Twist` — body-frame (vx, vy, wz) into the
  walking policy
- out: `goal_reached: std_msgs.Bool` — latched arrival

**Inner follower law** (in-process, python and rust produce identical bits):

```
update(pose: PoseStamped, path: Path, t, clearance: ndarray | None) -> Twist
```

One law per *track* — the input regime the follower is researched and judged
under. `hinted` gets the clearance array, `blind` does not and recovers the
same profile from the path's own stamps; `control/tracks.py` is the only place
that maps a track to its law, so the follower config, the CLI and the judge
never name a law directly. Interchangeable behind the signature above.

The path timestamps are NOT a schedule — only their deltas carry information
(slow segment = tight segment = track carefully), a follower must never chase
the clock, and running slower than the encoding is always legal. Third-party
Path producers/consumers interoperate; they just don't get the precision hint.
Because the encoding rides on the path itself it survives the blind track,
which is what makes blind a real deployment case rather than a handicap.
