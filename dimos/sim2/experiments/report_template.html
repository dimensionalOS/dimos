DimOS sim2 · experimental report · 2 November 2026

Should sim2 send snapshots or deltas?

We want a small, general simulation interface. Jeff proposes sending only changes to world state to avoid unnecessary work. Before that becomes the core interface, we need to establish which work it saves, which work it adds, and when that trade is worthwhile.

This report starts with the terms and the decision, explains the tests, then follows the evidence to a recommendation. It compares the reviewed implementations with two experimental controls. It does not assume that either existing implementation is the best possible version of its approach.

Reading order: concepts → hypotheses and method → five results → decision. Raw measurements and reproduction instructions are at the end.

1 · The problem we are solving

The simulator has the state. Other processes need to read it.

Imagine a robot standing beside a cup. Physics already maintains the robot's configuration and the cup's location. A camera renderer, controller or task evaluator may run in another process and need some of those values. The question here is how to turn native simulator data into a usable observation in that process.

That creates two separate choices: which physical facts to expose, and how to keep another process up to date. Sending fewer fields and sending fewer updates are different optimizations. We need to test them separately.

First, define the state we are talking about

TermMeaning in this report
Robot model / layoutThe relatively fixed description: body and joint identities, how links connect, and which array row belongs to which body or joint. Both sender and receiver need this context.
Link, joint and rootA link is a rigid part of a robot. A joint constrains motion between links; these experiments use hinge joints. The root locates a whole articulated robot in the world. A separate movable prop also has a root pose.
Pose and velocityPose means position and orientation. Body velocity contains linear and angular velocity; code often calls this a twist. Joint state here contains angle, angular velocity and actuator effort.
World-state sample / snapshotThe current values of an agreed set of fields at one simulation time. Here, consumers need root poses, root velocities and joint arrays. “Full” means complete for those fields, not every internal simulator variable, solver checkpoint, image or contact.
Delta / WorldChangeA message containing only the fields or groups selected as changed. Jeff sends their new absolute values. The receiver stores a local copy, called a mirror, and replaces those fields.

One change, two ways to communicate it

Suppose both processes already know that the robot base is at x = 0 m and the cup is at x = 1.0 m. The cup moves to x = 1.1 m; the robot stays still. To keep this example readable, the table shows just one position coordinate.

Message strategyNext message containsWhat the receiver does
Full sampleRobot x = 0; cup x = 1.1Use this complete current sample, with the known layout.
DeltaCup x = 1.1Replace the cup field in its mirror; retain the previously known robot field.

The delta does not say “add 0.1 m”, and it does not command physics to move the cup. It reports a value that physics already produced. Its advantage is fewer transmitted fields. Its dependency is the receiver's existing mirror: it must already have the other values and their identities. The initial complete copy is called a baseline.

A smaller full sample is a third option

Our current snapshot includes poses and velocities for every robot link. But given the robot model, its root pose and its joint angles, a reader can calculate its link poses. This calculation is called forward kinematics. A consumer needing roots and joints can therefore receive a compact full sample without receiving every derived link pose.

That leaves a precise architectural question: after removing unnecessary fields, does suppressing unchanged updates improve the service we need enough to justify its processing and synchronization requirements?

2 · How we test that question

Separate representation, suppression and delivery

A direct race between Pim's code and Jeff's code would mix several changes: different fields, encoding formats, Python operations and receiver structures. It tells us which tested path is faster, but not why. We therefore use four paths, with stable names throughout the report.

PathFields and deliveryPurpose
A · Pim fullCurrent snapshot: all link poses/velocities and joint arrays. Existing CBOR encoding, which converts the Python data into bytes.Measure our reviewed implementation.
B · Compact fullExperimental full sample of root poses/velocities and joint arrays. The same CBOR encoder.Test a smaller complete representation. This is a benchmark control, not a production change.
C · Jeff always-sendJeff's actual frame builder, generated LCM byte encoding and mirror, with comparison history cleared before every capture so groups are sent again.Control for D: removes change suppression, including its comparisons. It is not a shipped mode or a recovery fix.

C versus D tests the net cost of suppression within Jeff's implementation. A versus B is useful but also changes velocity-conversion code. After a profile revealed that difference, we added a separate control that varies link coverage and conversion code independently. The original hypotheses preceded the timing sweep; that additional control is a follow-up investigation.

3 · Results, in the order of the hypotheses

What the experiments establish

H1 · Representation

Sending fewer link rows helps when there are many links to remove

Test. We cross two independent choices: all-link versus root-only rows, and the original per-body numpy.roll velocity rearrangement versus direct slice assignment. Both conversion methods produce the same ordering. All four combinations use the same data format, encoder and consumer.

$controls_table

Elapsed milliseconds for capture, encoding and usable output; median of five trial medians. Each world also contains moving joints. “Roll” and “slices” differ in conversion code, not represented physical state.

Observation. With 32 chains, the same slice-based implementation takes $links_32_ms ms for all links and $roots_32_ms ms for roots only: about $representation_gain times less processing time. With one chain and 2,048 props, those two times are nearly the same. Almost every prop needs its own root row anyway.

The other comparison matters just as much: with 2,048 props, changing only the all-link velocity conversion reduces time from $roll_large_ms ms to $slice_large_ms ms. Therefore, attributing the entire A-to-B improvement to “compact world state” would be wrong.

Conclusion for H1: reducing derived link rows is a demonstrated benefit for the many-chain workload. A separate Python implementation cost explains most of the gain in the prop-heavy workload. We should improve both without confusing them.

H2 · Change suppression

Jeff's suppression saves bytes, but costs more local processing in this test

Test. C and D read the same root/joint values and use the same encoder and mirror. C sends groups every sample; D compares with its last-sent values first. The table shows the largest world with 1% of props moving.

$primary_table

One moving 29-joint chain + 2,048 props. Payload excludes the one-time identity declarations and network framing. A and B use a different byte format from C and D, so their differences are not a pure suppression comparison.

Observation. C → D reduces payload by $suppression_reduction%, from $jeff_full_bytes to $delta_bytes bytes. But elapsed local processing rises from $jeff_full_ms to $delta_ms ms, about $suppression_cost times as long. Against B, D sends $compact_reduction% fewer bytes but takes $compact_cost times as long locally. That second comparison evaluates the complete tested paths, including their implementation differences.

$activity_plots

Both vertical axes are logarithmic: equal vertical steps represent multiplicative changes. Horizontal positions are the five tested scene sizes, equally spaced. The left plot measures elapsed local processing; the right measures bytes per sample. With all props moving, D's payload saving over C nearly disappears.

Why does sending less take longer?

D still visits every root, extracts its pose and velocity, and compares those arrays before deciding whether to send them. In the separate 40-frame profile at 2,048 props, it called numpy.allclose 163,123 times. The comparison subtree accounted for roughly 84% of profiled elapsed time. The normal timing results above come from runs without that profiling overhead.

This is the difference between work proportional to the world size and output proportional to the changed values. If N is the number of roots and J the total scalar joint values, this implementation still scans work of order N + J. Its output may shrink to the changed groups. A large changed joint group still sends all of that group's values.

Full: extract current values → encode them
Delta: extract current values → compare with history → encode changed groups

Conclusion for H2: the bandwidth claim is supported. A local processing speedup is not supported for this implementation and workload. These measurements do not establish an inherent cost for every delta design: vectorized comparisons or native change tracking were not tested.

H3 · Delivery to another process

The byte saving becomes useful when transfer cost is large enough

Test. We send real encoded messages through the existing DimOS Zenoh implementation, with separate receiver processes. Every receiver acknowledges a decoded initial baseline before timing starts. Tests request 50 or 200 publications per second and use one or four receivers.

Here, achieved rate means how many publications the producer actually completes per second. Capture-to-usable latency starts before extraction and ends after the receiving process has decoded and reconstructed the requested arrays. The p95 column is the 95th-percentile latency described in the test plan.

Now make transferring bytes expensive

To test the other side of the tradeoff, we repeat delivery with 512 props and a 50 Hz target, adding a delay before each send equal to payload bytes ÷ configured bytes per second. This is a synthetic serial transfer model over the same actual local transport. It is not a measurement of a remote network.

$constrained_table

Observation. At the synthetic 10 Mbps setting, D sustains approximately 50 Hz while B falls to approximately 20 Hz. At 100 Mbps both sustain approximately 50 Hz, with p95 near 10 ms. The larger transfer saving at 10 Mbps outweighs D's local processing cost.

The simplest cost model makes the condition explicit. If processing and transfer happen serially, deltas help when the transfer time they save exceeds their extra processing time:

(full bytes − delta bytes) / link bytes per second
> delta processing time − full processing time

This is a conditional model, not a measured bandwidth crossover. Real systems can overlap stages. The synthetic delay also includes OS timer overshoot; it does not reproduce network latency, congestion, packet loss or Desktop behavior.

Conclusion for H3: a bandwidth-dependent benefit is demonstrated under the imposed delay model. The local-process measurements favor B. Choosing between them requires a real consumer's rate, latency and bandwidth budget, rather than assuming fewer bytes always means faster feedback.

H4 · Correctness after interruption

A mirror can be fast and still contain the wrong world

Test. We use the actual writer, encoded messages and mirror, but deliberately change delivery: attach a receiver after the initial declarations, omit the cup's final movement update, or apply an older frame after a newer one. Full-sample readers are supplied the known model/layout.

$recovery_table

The missed-update case illustrates the dependency. The sender announces that the cup moved by 10 cm, but the receiver does not get that announcement. The cup then stays still. Jeff's comparison is against what the sender last sent, not what the receiver successfully applied, so later messages need not repeat the new cup pose. The tested mirror remains wrong by 10 cm.

These are controlled failures, not observed random loss in the transport benchmarks. The $passed_tests passing checks cover normal reconstruction, integrated physics and other experiment gates. The three recovery cases are marked as expected failures in the tests, meaning they demonstrate acknowledged defects rather than successful recovery.

Conclusion for H4: this delta stream needs a baseline and a recovery protocol before consumers can rely on it after interruption. Full samples repair the tested missing-current-state cases, but do not automatically reject older packets or recover historical events. Those requirements must be stated separately.

A practical precedent for initial full state followed by differences is MoveIt's planning-scene monitor. The experiments here test our pinned code, not MoveIt.

H5 · Effect on the simulation loop

Optimizing state handling cannot remove the cost of physics

Test. We now advance actual MuJoCo dynamics: settle the scene, drive joints and apply side forces to 10% of the props. Every path uses the same 2 ms integration step and derived-state refresh, exporting once per ten steps. A fifth run disables state export.

We measure real-time factor: simulated time divided by elapsed time spent in the measured physics and state-processing work. A value of 1 means those kernels keep pace with simulated time; 0.2 means five seconds of measured work for one simulated second. Setup and validation are excluded.

$physics_plot

Observation. At 2,048 props, the physics-only control reaches $bare_rtf× real time; B reaches $compact_rtf× and D reaches $delta_rtf×. B already spends little of this heavy loop on state handling. Matching the physics-only control would improve its throughput by about $max_compact_gain%.

This is Amdahl's law: the effect of an optimization is limited by the fraction of total work it changes. If state handling occupies fraction f of a serial loop and becomes s times faster, overall speedup is:

overall speedup = 1 / ((1 − f) + f / s)

Amdahl's law reference. The graph shows that the fraction changes with workload and implementation; the approximately $max_compact_gain% estimate applies to B in this large contact-heavy case, not every simulation.

Conclusion for H5: the large contact-heavy world is already physics-limited with B. D adds avoidable processing in this shared loop, but improving state delivery alone would not make the largest scene real-time.

The maximum observed contact count was $peak_contacts. Separate validation produced identical hashes of sampled native position/velocity arrays for all five paths at all five sizes. This is a common coherent physics loop, not either project's unmodified module scheduler. Jeff's native loop does not perform the same derived-state refresh, so these numbers cannot rank complete shipped stacks.

4 · The decision supported by the evidence

Start with compact full samples. Treat delta delivery as a conditional optimization.

These experiments justify reducing unnecessary state and keeping a measurable full-sample baseline. They do not justify making a delta-only stream the definition of world state.

H1 shows that representation and implementation efficiency deserve separate attention. H2 shows that Jeff's current suppression saves bandwidth at a local processing cost. H3 demonstrates a condition where that trade pays off. H4 establishes recovery requirements. H5 prevents us from treating a state-path improvement as a whole-simulation speedup.

  1. Define the readable state first. Agree on fields, units, frame conventions, model/layout revision and coherent simulation time. For the tested consumers, roots plus joint arrays are a useful starting point. Other consumers may require additional fields.
  2. Use B as the performance baseline for the next implementation. It was the fastest local path tested here. Remove the redundant link work and costly per-body conversion independently. For consumers that need derived link poses, include the cost of calculating those poses before extending this conclusion to them.
  3. Make delta delivery answer an explicit requirement. If a consumer's bandwidth budget warrants it, compare an optimized delta implementation against that same baseline, including usable-state latency. Require successful attach, interruption and reset recovery before using the mirror for control or grading.

A readable WorldState contract does not require allocating every field or publishing the whole world on every physics tick. The choice of sample fields, publication rate and transport representation can be made separately. That keeps the backend interface understandable while leaving room for a justified optimization.

What remains unresolved: the best possible delta implementation; the bandwidth and freshness requirements of the actual Desktop/G1 consumers; full-stack policy and sensor performance; GPU or other physics backends; and total memory-copy traffic. We measured elapsed processing, payloads, delivery and a controlled physics loop on one Mac. Those limits prevent a universal verdict on snapshots versus deltas.
