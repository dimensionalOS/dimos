# G1 proof: physics truth, independent sensors, GR00T commands

This example drives a G1 beside a desk and loose box using the existing GR00T
balance/walk task. It exercises Option G: shared models, one physics owner,
WorldState observations, independent sensors and ActionCommand input. The generic
core imports no G1 policy or control coordinator.

```sh skip
uv sync --python 3.12 --extra sim --extra control --extra cpu
source .venv/bin/activate
dimos run unitree-g1-sim2 --daemon
dimos status
dimos shell
```

In the shell:

```python skip
from dimos.msgs.geometry_msgs.Twist import Twist
app.G1PolicyModule.move(Twist(linear=(0.2, 0, 0)), duration=2.0)
app.G1PolicyModule.arm_joint("g1/left_elbow_joint", 1.1)
app.SimModule.status()
app.SimCameraModule.statistics()
app.SimLidarModule.statistics()
```

Use `dimos restart` for a fresh episode and `dimos stop` to stop. The normal CLI
owns the whole blueprint. Restart recreates physics, sensors, control and the
preview map. There is no in-place SimModule reset RPC.

## Trace the code

1. [The blueprint](/dimos/robot/unitree/g1/blueprints/basic/unitree_g1_sim2.py)
   loads the prepared `sim2_g1_usd/world.usda` asset from Git LFS. It contains the
   G1, GR00T drive settings, desk, loose box and named attachment frames. The G1
   geometry originates in Jeff's prepared USD; conversion is an offline asset step.
2. Camera, lidar and IMU expose `get_usd()`. The scene `UsdManager` composes those
   device subtrees at the attachment frames. The lidar uses the real Mid360 driver's
   description. Physics, camera, lidar and policy call `get_scene()`/`get_asset()`;
   MuJoCo 4.0 loads that USD natively. Only the scene manager publishes the TF tree.
3. SimModule steps physics at 500 Hz and publishes complete `WorldState` at
   200 Hz. Every `BodyState` has pose, twist and physical acceleration. Named
   joint truth and optional CBOR properties share the acquisition time.
4. SimImuModule samples at 200 Hz and SimJointEncoderModule at 50 Hz.
   [G1PolicyModule](/dimos/robot/unitree/g1/sim2_policy.py) joins their standard
   sensor timestamps on 20 ms control boundaries. The simulation run UUID is
   read once through `SimModule.simulation_config()` during build. The existing GR00T task produces
   targets which the host publishes as `ActionCommand.joint_commands`.
5. Physics runs independently of the policy. A command applies on the next
   available physics step and remains valid for 100 ms from its acquisition.
   Expiry holds the joint's current position and warns; physics continues.
   GR00T weights load in the ordinary build phase, before physics starts.
   Slow inference or late sensing can degrade the walk and does not pause time.
6. The camera samples at 15 Hz. Its `SimCameraModule` supplies `get_usd()` and
   standard output ports; `CameraRenderModule` owns the shared scene and renders
   all listed camera devices. Add another device RPC name to its `cameras` tuple
   to reuse that owner. Device configuration and output wiring are read by RPC. The renderer
   publishes directly onto each device's existing output topics.
   Lidar emits rolling 10 Hz scans from 200 Hz
   pose history, a fitted four-channel Mid360 direction pattern and an approximate
   range/noise/dropout model. Its simulated rays still hit robot surfaces.

## Lidar and the preview map

```text
G1 USD mount + Mid360.get_usd description -> g1/mid360_link
WorldState -> SimLidarModule
  -> /lidar_raw : PointCloud2            sensor axes, scan-start timestamp
  -> /pointcloud : PointCloud2           registered using simulation truth
       -> existing VoxelGridMapper      unchanged downstream consumer
            -> /global_map              accumulated points in world
```

Each raw point carries its firing offset in nanoseconds and channel ID. Camera,
lidar, IMU, encoders and TF retain their standard message headers. The complete
WorldState and ActionCommand carry SampleHeader; they do not replace sensor
message formats.

The mapper is configured in the blueprint for CPU, 5 cm voxels and publication
every five scans (2 Hz). Its implementation is identical to the stack base.
The map is a preview of accumulated truth-registered points. It includes robot
returns and can retain trails of moving bodies. It is not an estimated or
robot-filtered navigation map.

The Point-LIO variant, estimator-specific TF rerooting, rolling self-filter and
visual-geometry filter extension are outside this stack. No changes remain in
`dimos/mapping`, Point-LIO, `UsdManagerPointClearing` or `RoboPlanBodyFilter` relative to the prerequisite base.
Those changes remain available in Git history at `b324f84912bb`, but that older
Point-LIO variant had an incompatible LCM pin after the standard-header rollback.

The vendor head mesh seals the lidar window. The head and the lidar's own housing (`g1/head_link`, `g1/mid360_link_body`)
are excluded from the lidar's private optical query. Physics, camera geometry and all other
robot occluders remain. Intensity and material reflectivity are not modeled.
The pelvis IMU uses ideal orientation; its gyro and specific force are acquired
by the independent sensor module.

## Desktop

Open dimOS Desktop and attach Controller to the running blueprint. Use `world`
as the fixed frame and `g1/pelvis` as the followed frame. `/color_image` is the
mounted camera, `/pointcloud` is the latest registered scan and `/global_map` is
the optional accumulated preview. `/cmd_vel` drives the GR00T demonstration host.
Robot descriptions and TF come from UsdManager.

The blueprint requests eight workers; physics, camera and lidar request dedicated
workers. The coordinator assigns the other modules. This is ordinary blueprint
deployment configuration, not a real-time scheduling guarantee.

## Verification

```sh skip
pytest dimos/robot/unitree/g1/test_sim2_observations.py -m 'not self_hosted_large' -q
```

The tests deploy the ordinary blueprint through the CLI configuration parser,
check independent camera/lidar/IMU measurements and a world-frame map, then
command a forward walk and elbow movement. A separate geometry test checks that
the Mid360 mount sees broad floor coverage. No estimator accuracy or robot
self-filtering claim is made by these tests.
