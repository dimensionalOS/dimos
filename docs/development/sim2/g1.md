# G1 proof: physics truth, independent sensors, GR00T commands

This example drives a G1 beside a desk and loose box using the existing GR00T
balance/walk task. The generic core imports no G1 code and changes no control
coordinator. The G1 policy module is a demonstration host, not hardware firmware.

```sh
uv sync --extra sim --extra control --extra cpu
source .venv/bin/activate
dimos run unitree-g1-sim2 --daemon
dimos status
dimos shell
```

In the shell:

```python
from dimos.msgs.geometry_msgs.Twist import Twist
app.G1PolicyModule.move(Twist(linear=(0.2, 0, 0)), duration=2.0)
app.G1PolicyModule.arm_joint("g1/left_elbow_joint", 1.4)
app.SimModule.reset()
app.SimModule.status()
app.SimCameraModule.statistics()
app.SimLidarModule.statistics()
```

Stop with `dimos stop`. The normal CLI owns the run; no private launch script.

## Trace the actual implementation

1. [The blueprint](/dimos/robot/unitree/g1/blueprints/basic/unitree_g1_sim2.py)
   defines one `G1_MODEL`: the existing `imu_in_pelvis` and `mid360_link` URDF
   mounts, plus a prototype torso camera frame. `MODELS`
   goes to UrdfManager. `SCENE` adds instance placement and drive parameters;
   it has no camera, lidar or IMU configuration. Each sensor gets its own config.
2. `UrdfManager.robot_models()` delivers resolved geometry through #4937's shared
   configuration before build. The policy reads its joint limits from that same
   delivery. Physics, camera and lidar bind the same `SCENE` to it.
   Meshes, policies, desk and the reused
   Mid360 calibration resolve through Git LFS; archives are pointers in the diff.
3. SimModule publishes one complete `WorldState` at 500 Hz: each body has one
   `BodyState` containing `pose: Pose`, `twist: Twist` and `acceleration: Accel`
   (linear and angular). Joint truth and
   optional `CborObservation` values share that timestamp. Scene gravity reaches
   the IMU once through shared configuration; it is not in the streamed sample.
   The independent IMU samples at 200 Hz; the encoder at 500 Hz. The policy
   receives their measured messages, not the physical WorldState.
4. [G1PolicyModule](/dimos/robot/unitree/g1/sim2_policy.py) joins the expected
   sources at exactly the same clock/epoch/time, on 20 ms control boundaries.
   It converts those readings to the existing GR00T task input and publishes a
   typed `ActionCommand.joint_commands: JointCommand[]` with desired position, velocity, gains and
   feedforward effort. It does not access native dynamics or private feedback.
5. Physics advances at 2 ms steps and waits at each control boundary for that
   boundary's command. Late inference slows simulation time. A finite deadline
   fault pauses it; there is no automatic reset. Repeated acquisitions reuse
   the sensor's measured value and policy's cached command.
6. Camera acquisition is 15 Hz of simulation time. Lidar scans are 10 Hz, with
   200 Hz motion history, a fitted Mid360 direction pattern (group decimation 10),
   and the reused range-dependent noise/incidence-dropout model. This does not
   model intensity or material reflectivity. Pelvis IMU attitude is explicitly
   ideal; its gyro/specific force are sensor outputs. A second SimImuModule
   samples at the Mid360 mount and publishes `/imu_raw` for Point-LIO.

## Mid360: mount, measurement, map

These are separate responsibilities:

```text
g1.urdf: mid360_joint -> g1/mid360_link          physical mount, defined once
WorldState -> SimLidarModule                   rolling ray acquisition
                 Mid360Scan                   fitted four-channel directions/times
                 MujocoRaycaster              distances + surface normals
                 Mid360Returns                approximate noise + dropout
              -> /lidar_raw: PointCloud2       raw points in g1/mid360_link axes
WorldState -> SimImuModule -> /imu_raw: Imu     acceleration/gyro at the same mount
```

Every raw point has its own `offset_time` in nanoseconds and `line` channel ID.
The cloud header is the scan-start acquisition time. No truth deskew or world
pose is supplied to Point-LIO. The simulated Mid360 IMU is deliberately colocated
with the laser, so its Point-LIO extrinsic translation is zero; this is not a
measurement of the real Livox internal IMU offset.

| Blueprint | `/pointcloud` producer | `/global_map` frame | Robot global TF owner |
| --- | --- | --- | --- |
| `unitree-g1-sim2` | SimLidarModule registers hits with simulation truth | `world` | UrdfManager |
| `unitree-g1-sim2-pointlio` | PointLio estimates motion from `/lidar_raw` + `/imu_raw` | `odom` | PointLio |

Both feed the existing CPU `VoxelGridMapper`; both clear the map on a new reset
epoch. The default is a truth-registered map for viewing and is **not SLAM**.
The Point-LIO blueprint disables truth-cloud publication. PointLio publishes
`odom -> g1/mid360_link`; UrdfManager reverses the internal edges on the path
back to the pelvis and publishes no `world -> pelvis` edge. Every robot frame
has one parent. Internal articulation still uses simulated truth for display;
it is not fed to the estimator.

To try the estimated map instead:

```sh
dimos stop
dimos --build-native run unitree-g1-sim2-pointlio --daemon
```

`--build-native` uses the repository's normal Nix native build for Point-LIO.
On this development checkout its updated native binary is already built, so
`dimos run unitree-g1-sim2-pointlio --daemon` works directly. Set Desktop's fixed
frame to `odom` for this variant (`world` for the default). The estimated frame
has its own origin; no identity `world -> odom` transform is invented.

### What was wrong

The old example invented `g1/lidar` instead of using the actual upside-down
Mid360 mount, published only world-coordinate scans, and included no map
producer. Using the real mount then exposed an asset issue: the vendor head
mesh seals the lidar window. The corrected scan uses the URDF transform (the
same transform the hardware helper now reads) and excludes only `g1/head_link`
from this lidar's optical query model. All other robot links remain occluders;
physics collisions and camera geometry are unchanged. That head exclusion is
a temporary approximation until the window is represented separately.

### Adding another Mid360

1. Give it a link and fixed joint in the shared robot model, or use
   `RobotModel.with_fixed_frame(...)` once when composing that model.
2. Add a `SimLidarModule` with `LidarConfig(frame_id=..., pattern=partial(Mid360Scan,
   calibration_path), response=Mid360Returns)` and unique output remappings.
3. For lidar-inertial estimation, add `SimImuModule` at its IMU mount and wire
   that device's two raw topics to one PointLio instance. Configure the actual
   laser-to-IMU extrinsics when they are not colocated.

Physics requires no Mid360-specific code. Real hardware uses the existing
Mid360 driver to publish the same raw message types; choosing real versus sim
is currently explicit blueprint composition, not automatic driver replacement.

## Desktop

Use the companion Controller draft and dimos-lcm revision. The sensor and TF
wire headers changed; the old Controller build cannot decode them.

Open `http://127.0.0.1:5555/?app=dim-controller`. Fixed frame: `world`; follow frame:
`g1/pelvis`. The usual drive control publishes `/cmd_vel` to the policy. Camera,
cloud and TF carry acquisition time/epoch. This Desktop draft uses raw LCM images
and clouds while the gateway compression codecs catch up; it is a local/LAN path.
Enable `/global_map` in Layers to see the accumulated cloud.

The robot mesh comes from UrdfManager. The desk/box are visible through camera
and lidar; a multi-model scene loader and arm-planner UI are not part of this PR.

## Option G acceptance, 2026-11-04

After the Mid360 fix, all three G1 checks passed in a fresh process (16.24 s):
truth-map and native Point-LIO stand/walk/elbow/reset, plus a static mount test
requiring broad floor coverage. Both map modes verify raw channel IDs, acquisition
clocks, correct map frames, single-parent TF and reset epochs. The combined suite
passed 62 checks but its two G1 cases timed out in the macOS camera renderer after
earlier renderer tests (Metal pipeline failures); the fresh G1 run passed. This
is not a map-accuracy benchmark or a claim of fully green CI.

The final G contract passed the native G1 stand, walk, elbow and reset test in
8.82 seconds, with all four sensor modules active. The core passed 31 component
checks and 16 deployed module/example checks. These exercise angular acceleration,
non-Earth gravity delivery, rotated IMU axes, CBOR addressing and payload rejection,
duplicate actions, joint expiry and reset epochs. WorldState reuses `sensor_msgs.JointState` for `joint_truth`, with matching nested
and outer acquisition headers across publication and reset. Message fixtures pass
in Python and TypeScript, including both acceleration vectors and 64-bit times.

## Option F acceptance, 2026-11-04

```sh
pytest dimos/sim2 dimos/robot/unitree/g1/test_sim2_observations.py \
  --import-mode=importlib -o addopts='' -q
```

The Option F G1 acceptance test passed in 10.68 seconds: native workers, a
two-second stand, three-second forward walk, elbow movement and reset/recovery
with all sensor modules active.
The policy now publishes `actions: Out[ActionCommand]`; sensor and WorldState
encoding is unchanged.
Core tests include resting/free-falling/rotating-offset IMU physics, calibrated
encoder sampling, PD/feedforward, joint-driven contact, coherent camera replay, rolling
scan gaps, command expiry, stale epochs and finite controller timeout. New deployed checks
cover CBOR operation replay, rejection without partial effects, and CBOR-only
actions leaving motor boundaries waiting.

### Earlier split-stream baseline, 2026-11-03

The following measurements predate Options E/F and were not repeated after combining
the observation streams. A separate ordinary CLI run stayed upright beyond 136
simulated seconds. Over
10.025 wall seconds it advanced at 0.939 real-time factor, produced 14.06 camera
frames/wall second and 9.28 scans/wall second, with no physics or sensor errors.

are measurements on this machine, not a load sweep or a real-time guarantee.

### Consolidated SimModule acceptance

After deleting the standalone `Simulation` layer, the same G1 acceptance test
passed in 9.34 seconds (2026-11-03): stand, forward walk, elbow command and
reset/recovery with all four sensor modules active. At that revision the blueprint passed
`controllers`, `motion_frames` and `joint_ids` directly to `SimModule`; G removes
`motion_frames` because every body carries its motion; the policy
imports `ControllerConfig` from `sim2/module.py`. The policy implementation,
physical backend and sensor algorithms did not change in this refactor.
