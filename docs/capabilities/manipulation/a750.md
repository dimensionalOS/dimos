# A-750 Robotic Arm

Support for the A-750 robotic arm includes visualization, a connection module, `A750Connection`, that talks to the real arm, and a keyboard teleop blueprint.

## Quick Start

Run the A-750 teleop stack on a real arm, giving its serial port:

```bash
dimos run keyboard-teleop-a750 --a750connection.device-path /dev/ttyACM0
```

This launches:

| Module | Role |
|--------|------|
| `KeyboardTeleopModule` | Publishes routed spatial EEF twist intent from the keyboard UI |
| `ControlCoordinator` | Runs a 100 Hz coordinator loop and `EEFTwistTask` |
| `A750Connection` | Drives the arm over `a750_control` and publishes its joint state |
| `ManipulationModule` | Loads the A-750 robot model in Drake and serves Meshcat visualization |

Open the Meshcat URL printed in the terminal, usually `http://localhost:7000`, to view the robot.

## Real Hardware

The blueprint drives a real arm only; there is no mock. Talking to the arm needs the `a750_control` binding, which dimOS does not install; see [Connection Module](#connection-module). Start by connecting the arm to your computer with a USB cable. On Linux, the device will likely appear as `/dev/ttyACM0`. You can also check `/dev/serial/` for stable symlinks to connected serial devices.

Pro tip: run this in a separate terminal while plugging in the arm to verify that the OS detects it normally:

```bash
dmesg -w
```

If the device appears but dimOS gets a permission error when opening it, you may need to add yourself to the `dialout` group:

```bash
sudo usermod -aG dialout "$USER"
```

After changing groups, log out and back in again, or start a new login shell, before retrying.

Give `A750Connection` the arm's serial port, after the blueprint name or as `A750CONNECTION__DEVICE_PATH`:

```bash
dimos run keyboard-teleop-a750 --a750connection.device-path /dev/ttyACM0
```

If no command arrives for 0.1 s (`--a750connection.deadman-timeout-s`), the connection tells the arm to hold where it is, and keeps re-sending that hold: the arm goes limp 0.2 s after its last command.

## Robot Model

The robot model and the coordinator's connection config are defined in
[`dimos/robot/manipulators/a750/config.py`](/dimos/robot/manipulators/a750/config.py).
The runnable keyboard teleop stack is composed in
[`dimos/robot/manipulators/a750/blueprints/teleop.py`](/dimos/robot/manipulators/a750/blueprints/teleop.py).

| Field | Value |
|-------|-------|
| Arm joints | `joint1` through `joint6` |
| Arm DOF | 6 |
| Gripper joints | `finger`, `finger_mimic` in the URDF; exposed as `arm/finger` by `A750Connection` |
| Base link | `base_link` |
| End-effector link | `gripper_base` |
| Home joints | `[0, 0, -90 deg, 0, 0, 0]` |
| Drake model | Pinned `a750_rev1.urdf` from `https://github.com/adob/a750_description` |
| FK/EEF twist task model | Same pinned model, with `joint1` through `joint6` controlled by the IK solver |

The runtime model and `a750_description` package root are resolved lazily through
a Git-backed robot description source handle pinned to an immutable commit.
Planning and FK/IK share this model. Both finger joint limits are adjusted to
`0–0.06 m` so the model accepts the zero-position gripper used at initialization.
Keyboard teleop does not load the model directly.

## Gripper

The blueprint configures a parallel-jaw gripper:

| Parameter | Value |
|-----------|-------|
| Open position | `0.06 m` |
| Close position | `0.02 m` |
| Collision exclusions | Imported from the A-750 MoveIt/SRDF collision pairs |

`A750Connection` reads and commands gripper position in meters using the `a750_control` Python binding.

## Connection Module

`A750Connection` is defined in [`dimos/robot/manipulators/a750/connection.py`](/dimos/robot/manipulators/a750/connection.py#L73).

| Part | What it does |
|------|--------------|
| Connect/disconnect | Opens `a750_control.Robot(device_path)` and starts its control loop; stopping the module disconnects |
| `position_command` | Joint targets in rad for `arm/joint1` to `arm/joint6`, and `arm/finger` in m; a joint left out keeps its last target |
| `joint_state` | Position, velocity and effort of the six joints and the finger, about 100 times a second |
| Hold | Holds the arm where it is from connecting until the first command, and whenever commands stop |
| Cartesian motion | Not in the arm; the coordinator's IK turns end-effector twists into joint targets |

The `a750_control` package starts a separate thread with real-time priority for its hardware control loop. That loop sends commands and reads back joint state at 1 kHz. `A750Connection` publishes the most recent state cached by that loop, so a reading may be up to 1 ms stale. The USB connection also adds roughly 1 ms of latency.

No dimOS extra installs the binding. It is a third-party package from the arm's
author, not the dimOS project: the source is at
https://github.com/adob/a750_control and PyPI publishes it as `a750-control`.
Review the package yourself before installing it into the environment that
runs dimOS:

```bash
uv pip install a750-control
```

If `a750_control` is not installed, `A750Connection` fails to start with an import error.

## Control Path

The `keyboard-teleop-a750` blueprint is defined in
[`dimos/robot/manipulators/a750/blueprints/teleop.py`](/dimos/robot/manipulators/a750/blueprints/teleop.py).

```text
KeyboardTeleopModule
  -> /coordinator_ee_twist_command TwistStamped
  -> ControlCoordinator EEFTwistTask
  -> A750Connection (a750_control)
  -> /coordinator_joint_state JointState
  -> ManipulationModule Drake/Meshcat visualization
```

The coordinator runs at 100 Hz. The lower-level `a750_control` binding runs its hardware control loop at 1 kHz once `A750Connection` has connected.

## Keyboard Controls

The A-750 teleop command uses the same keyboard controls as the other manipulator teleop blueprints:

| Key | Action |
|-----|--------|
| W/S | +X/-X |
| A/D | +Y/-Y |
| Q/E | +Z/-Z |
| R/F | +Roll/-Roll |
| T/G | +Pitch/-Pitch |
| Y/H | +Yaw/-Yaw |
| ESC | Quit |

## Known Limitations

- Joint limits come from the pinned URDF.
- EEF twist commands are integrated and solved by the dimOS coordinator task, not by a native Cartesian mode in the arm.
- Force/torque data is not exposed yet.
- Real hardware mode depends on the external `a750_control` package and a reachable serial device.
